为什么 VAD 放在 NS 之后：它看到的是降过噪的信号，信噪比比原始麦克风好；而 AEC 必须拿原始 mic 和播放参考做自适应，所以 AEC 只能在最前面。顺序固定为 AEC → NS → VAD。
为什么不用 AFE 一体化：esp_afe_sr 在本机 fetch 恒定 ret=-1，换类型、调优先级、过 config_check、改 ringbuf 都无效，详见 esp32s3-afe-integration_workflow.html 的失败记录。这里退回独立 API，AEC/NS 的参数一行没动，风险最小。
两位 flags 是必须的：只给 bit0 的话，「老固件」和「VAD 判为静音」都是 0，PC 端会把老固件永远当成静音、一句都切不出来。
闭环：AEC → NS → VAD → flags → PC 切句 → 转写 → 回读 → 被麦克风收回。回读那一环靠设备端 AEC 压掉（实测播放期间上行平均 RMS 97，底噪 104），再叠加 PC 端的文本去重与刹车。
vad_create 失败VAD 起不来：上行 flags 恒 0，PC 端 hint=None 自动走能量阈值——就是今天之前的行为，不会变差。
播放声被判成人声全双工时板子自己的声音可能触发 VAD：文本去重 + 连续 3 次刹车兜底；仍频繁就切回半双工（mic_gate=on）让朗读期间静音。
稳态噪声被判成人声风扇/空调持续起句：VAD_MODE_1 已偏激进，仍误判就提到 VAD_MODE_2 或 VAD_MODE_3（改一行常量）。
老固件 / 老 PC 端混用老固件 flags 恒 0 → bit1 为 0 → PC 走能量阈值；新固件配老 PC 端 → 老代码不读 flags，行为不变。
VAD 切点与 20 ms 帧边界VAD 原生支持 10/20/30 ms，这里每帧正好 20 ms，不需要重分块，也不增加延迟。
边界与约束
  • 改动：新增 main/audio_vad.cc/.h；audio_transmitter.cc 在 NS 之后调 VAD 并写 flags；audio_speaker.cc 的 STAT 换成 vad= 字段；components/tarot_core/src/lib.rs 的包头加 flags 形参。
  • AEC / NS 的实现与参数一行未动，VAD 只是追加在最后。
  • 包头 20 字节不变，只占用原本恒 0 的 flags 位。
  • 不做：AFE 的 AGC、唤醒词、多麦阵列、设备端切句（切句仍在 PC 端做）。
验收结果（2026-10-29）
  • 上行 50 pkt/s 稳定（连续 20 秒每秒 49~51），1000/1000 包都带 VAD 结论，其中 153 帧判为语音。
  • STAT：aec=on ns=on vad=on，vad_frames 持续增长，vad_speech=317；inner_free 181 KB → 222 KB（AFE 卸载后回补）。
  • PC 端 hint 随说话增长：41/734 → 117/1236 → 881/5983，停止说话后冻结不动。
  • 关键证据：切出的句子 utterance rms=42~73 而能量阈值 thr=66~74——正是能量 VAD 切不出来的那批低声句子。
  • 端到端：说话期间产生新转写（15:07:17、15:07:52），VAD → flags → PC 切句 → STT 全链路通。
  • 离线回归 21 项全 PASS，含 3 项 hint 路径用例。
验收标准
  • 上行 50 pkt/s、丢包 0，STAT 报 vad=on 且 vad_frames 持续增长。
  • 静默时 vad_speech / vad_frames 接近 0；说话时明显上升。
  • PC 端日志 hint=语音帧/总帧 非零，说明 flags 真的被用上了。
  • 回退可用：flags 恒 0 时 PC 仍能靠能量阈值切句。
