带宽账：原始 16 kHz × 16 bit = 32 KB/s（256 kbps）；ADPCM 4:1 后 8 KB/s（64 kbps），加 6 字节头 = 66 kbps。双向同时跑共 132 kbps，实测上下行并行不丢帧。为什么必须压：直传原始 PCM 会踩着带宽上限跑，一次重传就掉音。
为什么每帧独立编码：ADPCM 是差分编码，跨帧预测一旦丢包，后续会持续失真直到重新同步。每 20 ms 重置一次预测器和步长，丢一包只坏 20 ms，代价是信噪比掉一点点（语音听不出来）。上下行共用同一套表和同一套帧格式。
为什么下行也走 BLE：回读（把转写结果念出来）如果还走 UDP，就得同时开 Wi-Fi 和 BLE，两者抢射频；干脆复用已建立的 BLE 链路，一根通道两向跑，也不占路由器。
上行链路：采集 → AEC → NS → VAD → ADPCM → BLE 通知 → PC 解码 → 切句 → 转写。下行链路：转写结果 → SAPI 合成 → ADPCM → 写特征 RX → 板子解码 → I2S → 扬声器，同一帧同时喂 AEC 参考，避免自己放的声音被采回来再转写一遍。VAD 结论通过包头 1 字节 flags 走同一条 BLE 通道（bit1 有效 / bit0 语音），PC 端处理逻辑与 UDP 模式完全共用——它只认 on_audio(pcm, flags) 这个接口。
MTU 协商偏小对端只给 23 字节 MTU 时，166 字节一包塞不进：自动降级为把一帧拆成多个通知，并在 STAT 里报当前 MTU，便于判断是不是退化模式。
通知拥塞PC 处理不过来（解码/转写卡顿）：板子侧丢弃最旧帧并计数，界面显示丢帧数——宁可少几帧也不让 BLE 缓冲区涨到几百毫秒延迟。
ADPCM 丢包每帧独立编码，丢一包只坏 20 ms；seq 只用于统计丢帧，不做重排（BLE 链路层已保证顺序和重传）。
连接断开板子重新广播；PC 端记住设备地址后按地址直连重试（间隔 1.5 s），首次连不上才退回扫描，实测重连约 2.8 秒；期间界面显示「蓝牙断开」，不静默卡住。
Wi-Fi 与 BLE 共存抖动两者共用射频会互相抢：做成二选一模式（配置决定），不同时开，避免排查不清的丢帧。
PC 没有可用蓝牙适配器不支持/驱动缺失：input_mode 切回 udp，原有 Wi-Fi 链路功能不退化。
下行播报时链路已断写特征失败/连接已掉：Speaker 直接报「下发失败：链路已断开」，不阻塞转写主流程；板子侧 drop_fail 单独计数（实测 0），不与「没连 PC 的空跑丢弃」混在一起。
下行自激（扬声器被自己采回）I2S 写之前把同一帧喂 AEC 参考通道。实测让板子念 6.2 秒 TTS、同时录下整段上行送讯飞，转出的是「谢谢我的生活」这类噪声幻觉，原句一个字都没复现；放音期间上行仍是 50.1 包/秒、丢帧 0。
边界与约束
  • 板端：开 CONFIG_BT_ENABLED + NimBLE；新增 main/audio_ble.cc/.h（GATT 服务 + ADPCM 编解码 + 双向收发）；audio_transmitter.cc 把帧交给 BLE 而不是 UDP；audio_speaker.cc 拆出 speaker_init_hw / speaker_start_i2s_only / speaker_write，BLE 模式不建 UDP 下行任务。
  • PC 端：新增 micapp/ble_receiver.py（与 UdpReceiver 同接口）、micapp/adpcm.py（编解码）；config.json 加 input_mode；tts.Speaker 加 BLE 通道。
  • 不改：采集、AEC、NS、VAD、切句、转写、回读策略、落盘一条都不动——BLE 只替换「音频怎么到 PC」这一段。
  • AUDIO_LINK=udp|ble 写在 audio.env 里，避免换了终端就编出另一种链路。
  • 参照 IDF 自带示例：ble_spp（自定义传输）、ble_phy（2M PHY）、bleprph_wifi_coex（共存）。
  • 不做：手机 App、BLE 配对加密绑定、LE Audio/LC3（S3 在 IDF 5.3 不支持）、多板同时连接。
待决问题
  • 设备广播名：倾向 MicDesktop-XXXX（后四位取 MAC），方便多块板子区分。已按此实现。
  • 连接间隔：倾向 15 ms（50 包/秒下约 76% 的连接事件被占用）。实测 RTT 中位 21.4 ms——一次 PING 会排在音频包后面，再压低间隔收益有限。
  • ADPCM 变体：倾向 IMA ADPCM（无授权、解码十行代码、误差小）。已实现，上下行共用同一套表。
验收结果（2026-10-29）
  • 板子广播 MicDesktop-0EB6，PC 扫描可见并连接，MTU 协商到 247（166 字节音频包一包发完，不分片）。
  • 探针 12 秒：601 包 / 50.1 包每秒，丢帧 0，601 包全部带 VAD 结论，其中 16 包判为语音。
  • 桌面端 BLE 模式：日志 input mode: ble，vad n 持续增长（5 秒 241 帧 ≈ 48 包/秒），hint 随说话增长，已用设备端 VAD 切句（utterance 1.24 s）。
  • ADPCM 离线往返 31~37 dB（1 kHz 34.3 / 440 Hz 小音量 36.8 / 300 Hz+噪声 31.6），全零帧、头字段、短包三类边界都过。
  • 修正一 · 广播包超长：128 位 UUID(18B)+完整名(17B)+flags 超过 31 字节，ble_gap_adv_set_fields 返回 rc=4(EMSGSIZE) 且不广播；改为名字放扫描响应。
  • 修正二 · 板子每秒重启：跳过 Wi-Fi 后 speaker_start() 仍建 UDP 下行监听，lwIP 断言 tcpip_send_msg_wait_sem (Invalid mbox)，GATT 发现永远完不成，PC 侧只看到连接超时；BLE 模式下不启动扬声器下行。
  • 修正三 · ADPCM 漏写符号位：delta 未并进 sign，解码端只加不减会漂到满幅，听起来是纯噪声、极易误判成丢包；离线往返测试发现。
  • 下行 TTS（已验证）：3.7 秒语音共 185 帧，板子 STAT rx=185——一帧不少；同期上行 49.8 包/秒同时进行，走的是真实 Speaker → SAPI → BLE 路径。
  • 控制帧统一（已验证）：RX 特征同时接文本控制帧，与 UDP 侧同名同义——STAT / TONE / NS:on|off / PING。实测 NS:off → 回 NS off、NS:on → 回 NS on，STAT 回包正常；界面底栏的降噪 A/B 按钮与手动朗读在蓝牙模式下都能用。
  • 断线自动重连（已验证）：esptool 硬复位板子 → 18.4 s 检测到断开、21.2 s 重连成功、24 s 恢复 50 包/秒，全流程约 2.8 秒、重连后零丢帧。原来每次重连都要先扫 5 秒再加退避，实测要 17 秒；改成记住地址直连后压到 3 秒内。
  • 全双工（已验证）：下行 2.00 秒提示音期间上行 126 包 / 50.1 包每秒、丢帧 0。两种丢弃分开计数后 drop_fail=0（drop_nolink 是没连 PC 时空跑，不算问题）。
  • 延迟（已验证）：PING/PONG 30/30 收到，RTT 最小 4.2 / 中位 21.4 / p95 84.6 / 最大 90.4 ms，单向链路约 10.7 ms。RTT 含音频包排队，所以明显大于 15 ms 连接间隔。
  • 修正四 · PING 无回包：板子把整条命令回显成 PONG（非 NUL 结尾的 buf 直接 %s），token 错位成 "PING"，PC 永远匹配不上；改为跳过前缀并拷进带终止符的缓冲。
  • 修正五 · RTT 被量化：Windows 上 time.monotonic() 精度约 15.6 ms，量出 0/16/31 的假分布；换 perf_counter 才得到 4.2~90.4 ms 的真实分布。
  • ADPCM 对转写的影响（已验证）：6 句已知文本 × 干净 / 加噪 SNR 20 dB 两种条件，原 PCM 与 ADPCM 往返各转写一次，12 次结果全部逐字相同（连「三点→3点」这种数字归一化差异都一致），平均字错率 10.6% 对 10.6% —— 4:1 压缩在转写上看不出代价。
  • 自激验证（已验证）：让板子念 6.2 秒 TTS，同时录下整段上行再送去讯飞 —— 转出「谢谢我的生活。」这类噪声幻觉，原句一个字都没复现，AEC 把播报消干净了。
  • 自激余量（值得注意）：放音期间上行 RMS 从 22.7 涨到 62.3，但提示音 880 Hz 分量反而降到基线的 0.2 倍、1320 Hz 仅 5e-5，说明涨的是宽频机械噪声不是内容。不过 62.3 与当前阈值 63 只差不到 1，底噪很低的房间里播报残响有可能擦线切出一句噪声——Readback 的去重与刹车会挡掉，代价只是一次白转写。
  • 边界：ADPCM 与自激两条用的是 SAPI 合成音 + 人工白噪，只能证明「压缩本身不掉字」「播报不会被原样采回」，不能替代真人 / 真实房间的样本。
验收标准
  • 板子上电后 PC 能扫到并连上，20 秒内开始收到音频。
  • 上行稳定 50 帧/秒，连续 60 秒丢帧 < 1%。
  • 转写结果与 Wi-Fi 模式下同等可读（同一句话对比）。
  • 拔掉板子电源再上电，PC 自动重连并恢复收音频。
  • 端到端延迟与 Wi-Fi 模式相比不劣化超过 100 ms。
