带宽账：原始 16 kHz × 16 bit = 32 KB/s（256 kbps）；ADPCM 4:1 后 8 KB/s（64 kbps），加 3 字节头 = 65 kbps。BLE 5.0 在 2M PHY 下能跑几百 kbps，留了 4 倍余量——这不是优化，是必须：直传原始 PCM 会踩着带宽上限跑，一次重传就掉音。
为什么每帧独立编码：ADPCM 是差分编码，跨帧预测一旦丢包，后续会持续失真直到重新同步。每 20 ms 重置一次预测器和步长，丢一包只坏 20 ms，代价是信噪比掉一点点（语音听不出来）。这是丢包容错换编码效率，值得。
为什么只做上行：下行 TTS 也是 32 KB/s，同样要压，工作量翻倍。本轮先把「能用蓝牙说话」跑通，回读留到下一轮。
链路：采集 → AEC → NS → VAD → ADPCM → BLE 通知 → PC 解码 → 切句 → 转写。VAD 结论通过包头 1 字节 flags 走同一条 BLE 通道（bit1 有效 / bit0 语音），PC 端处理逻辑与 UDP 模式完全共用——它只认 on_audio(pcm, flags) 这个接口。
MTU 协商偏小对端只给 23 字节 MTU 时，163 字节一包塞不进：自动降级为把一帧拆成多个通知，并在 STAT 里报当前 MTU，便于判断是不是退化模式。
通知拥塞PC 处理不过来（解码/转写卡顿）：板子侧丢弃最旧帧并计数，界面显示丢帧数——宁可少几帧也不让 BLE 缓冲区涨到几百毫秒延迟。
ADPCM 丢包每帧独立编码，丢一包只坏 20 ms；seq 只用于统计丢帧，不做重排（BLE 链路层已保证顺序和重传）。
连接断开板子重新广播；PC 端退避重连（1/2/4/8 s，上限 10 s），期间界面显示「蓝牙断开」，不静默卡住。
Wi-Fi 与 BLE 共存抖动两者共用射频会互相抢：做成二选一模式（配置决定），不同时开，避免排查不清的丢帧。
PC 没有可用蓝牙适配器不支持/驱动缺失：input_mode 切回 udp，原有 Wi-Fi 链路功能不退化。
边界与约束
  • 板端：开 CONFIG_BT_ENABLED + NimBLE；新增 main/audio_ble.cc/.h（GATT 服务 + ADPCM 编码 + 通知发送）；audio_transmitter.cc 把帧交给 BLE 而不是 UDP。
  • PC 端：新增 micapp/ble_receiver.py（与 UdpReceiver 同接口）+ ADPCM 解码；config.json 加 input_mode。
  • 不改：采集、AEC、NS、VAD、切句、转写、回读、落盘一条都不动——BLE 只替换「音频怎么到 PC」这一段。
  • 参照 IDF 自带示例：ble_spp（自定义传输）、ble_phy（2M PHY）、bleprph_wifi_coex（共存）。
  • 不做：下行 TTS 走 BLE、手机 App、BLE 配对加密绑定、LE Audio/LC3（S3 在 IDF 5.3 不支持）。
待决问题
  • 设备广播名：倾向 MicDesktop-XXXX（后四位取 MAC），方便多块板子区分。
  • 连接间隔：倾向 15 ms（50 包/秒下约 76% 的连接事件被占用，比 7.5 ms 省电、比 30 ms 有余量）。
  • ADPCM 变体：倾向 IMA ADPCM（无授权、解码十行代码、误差小）。
验收结果（2026-10-29）
  • 板子广播 MicDesktop-0EB6，PC 扫描可见并连接，MTU 协商到 247（166 字节音频包一包发完，不分片）。
  • 探针 12 秒：601 包 / 50.1 包每秒，丢帧 0，601 包全部带 VAD 结论，其中 16 包判为语音。
  • 桌面端 BLE 模式：日志 input mode: ble，vad n 持续增长（5 秒 241 帧 ≈ 48 包/秒），hint 随说话增长，已用设备端 VAD 切句（utterance 1.24 s）。
  • ADPCM 离线往返 31~37 dB（1 kHz 34.3 / 440 Hz 小音量 36.8 / 300 Hz+噪声 31.6），全零帧、头字段、短包三类边界都过。
  • 修正一 · 广播包超长：128 位 UUID(18B)+完整名(17B)+flags 超过 31 字节，ble_gap_adv_set_fields 返回 rc=4(EMSGSIZE) 且不广播；改为名字放扫描响应。
  • 修正二 · 板子每秒重启：跳过 Wi-Fi 后 speaker_start() 仍建 UDP 下行监听，lwIP 断言 tcpip_send_msg_wait_sem (Invalid mbox)，GATT 发现永远完不成，PC 侧只看到连接超时；BLE 模式下不启动扬声器下行。
  • 修正三 · ADPCM 漏写符号位：delta 未并进 sign，解码端只加不减会漂到满幅，听起来是纯噪声、极易误判成丢包；离线往返测试发现。
  • 未验证：BLE 模式下真实说话的转写质量、断线自动重连、端到端延迟。
验收标准
  • 板子上电后 PC 能扫到并连上，20 秒内开始收到音频。
  • 上行稳定 50 帧/秒，连续 60 秒丢帧 < 1%。
  • 转写结果与 Wi-Fi 模式下同等可读（同一句话对比）。
  • 拔掉板子电源再上电，PC 自动重连并恢复收音频。
  • 端到端延迟与 Wi-Fi 模式相比不劣化超过 100 ms。
