为什么换 AFE 而不是继续调阈值：能量 VAD 只看响度，今天实测已经证明它和「是不是人声」不是一回事——底噪在 18~25 之间漂，阈值就得跟着调一整天。AFE 的 VAD 是基于频谱特征的判定，而且它看到的是 AEC 之后、降噪之后的信号，天然比 PC 端拿到的更干净。
AGC 是额外收获：2–3 米的小声说话被自动抬起来，这比把阈值一再压低更干净——压低阈值是让噪声也进来，抬升语音是让信噪比变好。
协议向后兼容：包头 20 字节一个字节都不改，只用 flags 里原本恒为 0 的位——bit1 = 本帧带设备端 VAD 结论，bit0 = 该结论是语音。为什么要两位：只给 bit0 的话，「老固件」和「AFE 判为静音」都是 0，PC 端没法区分，会把老固件永远当成静音、一句都切不出来。
AFE 内部自己开 se 任务和 ringbuf：采集任务只负责 feed，另一个任务取 fetch。时间戳对齐由 AFE 的 ringbuf 负责，我们不再手工维护 320↔512 的参考对齐。
AFE 初始化失败模型缺失、PSRAM 不够、afe_config_init 返回 NULL：自动回退到现有手工 audio_aec+audio_ns 链路，STAT 报 afe=off，上行照常。
CPU 超过 45% 线AFE 比手工链路重：实测若平均超线，按 关 AGC → 关 NS → AFE_MODE_LOW_COST 的顺序降档；仍超就整条回退并在交付里写明数字。
参考通道欠载没人播放时环形缓冲是空的：AFE 仍需每帧参考，按静音填 0 送入；AEC 在无参考时等价于直通。
fetch 超时或返回错误该帧输出用上一帧的样本补，不阻塞上行；连续失败 10 帧则停 AFE、回退手工链路。
老固件 / 老 PC 端混用老固件 flags 恒 0 → 新 PC 端走能量阈值；新固件 + 老 PC 端 → 老代码忽略该位，行为不变。
VAD 误判（播放声被判成人声）全双工时扬声器声音可能触发 VAD：AFE 自带 vad_mute_playback 开关，实测确认是否需要打开；另保留 PC 端能量阈值作交叉校验。
边界与约束
  • 改动：main/audio_afe.cc/.h（新增）、audio_transmitter.cc（采集/fetch 接线）、audio_speaker.cc（STAT 加字段）、main/CMakeLists.txt；PC 端 udp_receiver.py 解析 VAD 位、vad.py 支持 hint。
  • 手工 audio_aec.cc/audio_ns.cc 一行不删——既是回退路径，也是对照实验的基线。
  • se_init = false（单麦，没有阵列）；wakenet_init = false（本轮不做唤醒词）。
  • afe_type = AFE_TYPE_FD（全双工，含非线性降噪）；afe_mode = AFE_MODE_LOW_COST。
  • 不做：唤醒词、离线命令词、多麦阵列、设备端 AGC 之外的增益策略。
待决问题
  • AGC 要不要开？开的话安静处噪声也会被抬起来，可能让 PC 端能量阈值失效——倾向开，因为 VAD 位不再依赖能量。
  • 上行只带 VAD 位，还是顺带带 data_volume？后者要改包头，倾向不带，需要时从 STAT 看。
  • AFE 任务放哪个核？倾向 core 0（Wi-Fi 在 core 0，音频采集在 core 1，避免和采集抢）。
验收标准
  • AFE 版固件：上行 50 pkt/s 零丢包，STAT 报 afe=on se=off aec=on ns=on vad=on agc=on。
  • CPU 平均 ≤45%、峰值 ≤60%（和现在同一口径）。
  • 2–3 米说话时上行 flags bit0 稳定置位；静默时不置位。
  • PC 端在 VAD 位存在时不再依赖能量阈值，阈值读数只作参考。
  • 回退路径可用：故意让 AFE 初始化失败，确认自动退回手工链路且上行不断。
