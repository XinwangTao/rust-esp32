当前模式 + 判定依据
分支来自同一个 decide：aec=on → 全双工；aec=off、回包不认识、探测超时 → 半双工（安全默认）。
两条分支最终都汇入同一条链路，区别只在 UdpReceiver 的下游是谁：slicer.feed 还是 MicGate。
一次性判定：整条流程只在启动时跑一遍。运行期不重探、不热切换——板子换了固件就重启 PC 端。
板子不在线没上电 / 不同网段 / 3 次超时：按半双工启动，界面提示「未探测到板子，先按半双工」。
老固件回包里没有 aec= 字段：视为 aec=off，装 MicGate。
配置写了显式值mic_gate=on|off：跳过探测，完全按配置来。
探测干扰播放只在启动时探一次、只发 4 字节；之后再也不发探测包。
运行中换了固件不热切换；下次启动重新探测才改模式。
为什么不直接用配置
  • 现状：dist/config.json 里写死 "off"。一旦板子刷回旧固件（比如排查问题时回滚），配置不改就会把回声当人声转写——错误无声无息。
  • 现状：代码默认是 "auto"（装门控）。新固件明明支持全双工，却仍然静音麦克风，白白丢掉「边说边播」的能力。
  • 两种错法都靠人记忆纠正，改成「问板子要能力」就不用记了。
边界与约束
  • 只改 mic-desktop 启动逻辑（main.py + micapp/gate.py 的 build_gate）；板子固件一行不动。
  • 只读 STAT，不发 TONE/PIN:/TARGET: 等会改变板子状态的控制帧。
  • config 显式 on/off 永远优先，保人工作业口。
  • 失败一律偏安全：宁可多静音，也不让回声变重复转写。
  • 不做：周期性健康检查、运行期热切换、多板子选择。
验收结果（2026-10-29，实机）
  • 探测成功：广播 STAT → 0.11 s 收到回包，state=True，来源 192.168.237.168（顺带完成板子发现）。
  • 超时兜底：对不存在的 IP 探测，3×0.4 s = 1.22 s 后返回 None → 半双工。
  • 启动实测：新 EXE 在 mic_gate=auto 下 0.94 s 完成判定，日志 mic gate: 板子上报 aec=on：全双工，不装门控；界面芯片「模式 全双工」，底栏显示判定依据；上行 51.0 pkt/s、丢包 0。
  • 回归：6 条判定分支（显式 on/off、aec=on、aec=off、超时、缺省键）+ 4 条回包解析全部 PASS。
实现修正（2026-10-29，实测发现）
  • 广播 STAT 不可靠：板子开着 Wi-Fi 省电（wifi:pm start, type: 1），广播包落在休眠窗口里就丢。实测同一时刻：广播 3 次全超时（3.02 s），单播 0.06 s 就回。原图「board_ip 为空就发广播」被判错，EXE 因此误判成半双工。
  • 改为：先取 config.board_ip；没有就在接收线程启动前短暂占用上行端口（≤1 s），从 AUD0 包的来源地址学到板子 IP，再单播 STAT；广播只当兜底。
  • 判定语义与失败出口都不变（aec=on → 全双工，其余 → 半双工），变的只是「怎么找到板子」。
  • 修复后实测：启动 0.82 s 完成判定，日志 mic gate: 板子上报 aec=on：全双工，不装门控，界面 48.4 pkt/s / 丢包 0。
已决问题
  • 探测失败（板子不在线）→ 按半双工启动，界面底部写明「未探测到板子，先按半双工」。
  • 界面 → 显示：顶部芯片给「模式 全双工/半双工」，底栏常驻判定依据，芯片 tooltip 同文。
  • config.mic_gate 代码默认值 → 保持 "auto"（语义已是「按探测走」，换个名字比改默认值更容易误导）。
